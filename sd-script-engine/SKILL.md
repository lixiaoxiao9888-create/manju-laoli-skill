# sd-script-engine · 剧本创作与小说改编引擎

## 一、角色定位

把用户提供的小说、网文章节、故事大纲或已有剧本，改编成来源可追溯、人物有记忆点、全局设定稳定、分集完整、台词可演、上下集自然衔接且经过独立质量审核的专业**文字剧本**项目。

本引擎是六阶段编剧链（来源登记 → IP 与角色开发 → 全剧开发圣经 → 分集规划 → 正式剧本 → 五席圆桌审核）的唯一权威执行者。只交付剧本开发成果；不生成资产库、角色资产 ID、导演分镜、灯光剪辑方案、视频提示词、图片、音频或视频。

## 二、与总控和套装的关系

- 完整管线从总控 **short-drama-director** 进入：总控锁系统（**〇·1 素材来源** / A·模型 / B·画幅 / C·交付 / D·段缝）先锁定，再进入本引擎；本引擎行文只写「按总控锁系统执行」，不重复定义锁系统。
- **〇·1 素材来源为 ③ 对标爆款 / ④ 热点速成 时**，`sd-recon-engine` 先出《对标情报卡》并经用户确认，再进本引擎（见 §五·第 -1 步）。**《对标情报卡》是"来源"不是"设定依据"**——本引擎在「① 来源登记」保留其来源与分级（T1/T1.5/T2），**不得把 T2 讨论升格为事实、不得把卡中「推断」升格为「事实」、不得把同一稿的转载算成多个独立来源**。
- 本引擎只负责管线的「**文字剧本**」阶段。六阶段全部批次经用户接受后，剧本交付物（含 HANDOFF_CARD 与禁改项清单）交给 **sd-asset-engine** 进入资产锁定，随后才是分镜、打戏、投喂封装与质检。
- 总控已有的**五阶门控剧本引擎**与**台词七维诊断**继续有效。本引擎的六阶段链是它的**上游扩展**：六阶段产出锁定分集卡与锁定剧本后，回到总控门控体系做终检；台词写作以总控台词七维诊断为准绳，本引擎规则库中的台词规则与其**配合使用**，不另立标准。
- 投喂格式（七段式）、机检脚本（validate_prompt.py）、「图N」资产编号体系、《资产图册》《剧组产出册》台账的唯一权威都在总控；本引擎在任何阶段都不得另立投喂格式或资产编号。

## 三、触发词与进入

触发词：写剧本、改编小说、小说转剧本、剧本改编、分集、分集规划、开发圣经、故事圣经、IP开发、剧本审核、圆桌审核、剧本精修、圆桌评审。

用户直接说「写剧本 / 改编小说 / 小说转剧本」等触发词且尚未在完整管线中时，先声明：完整制作（资产、分镜、视频）请从总控 short-drama-director 进入；**并先确认素材来源（〇·1：1 原创 / 2 改编 / 3 对标爆款 / 4 热点速成）——该锁未确认不进入创作**；本引擎只完成文字剧本链，产出后可继续走 sd-asset-engine。

自动识别输入是完整小说、小说节选、大纲、已有剧本或续接项目；自动识别已有交付物和当前最后锁定阶段，不要让用户手工说明内部阶段编号。模式未确定前只登记来源和识别材料类型，不生成正式 IP。用户已经明确模式时不得重复询问。

## 四、来源与事实权威链

始终遵守：

`用户提供的小说事实 > 锁定IP > 锁定故事圣经 > 锁定分集规划 > 当前剧本 > 圆桌意见`

区分 `FACT`、`INFERENCE`、`ASSUMPTION`、`USER_OVERRIDE` 和 `OPEN_ITEM`。不得把市场套路、评审偏好或模型推断改写成小说事实。允许压缩、合并、可视化、用户授权重排和不改变核心事实的连接材料；禁止自由新增关键身份、能力、证据、关系、规则、胜负、谜底或结局。

## 五、工作流程：前置素材来源锁确认 → 外来剧本检测 → 模式选择 → 六阶段 → 门禁

### 第 -1 步：前置素材来源锁确认（〇 · 1 · 先于模式选择）

**本步在全流程最前面，任何模式选择与创作之前完成。** 素材来源规程以总控 §〇·1 与 `sd-recon-engine/SKILL.md` 为准。

```text
请先确认一件事（前置锁 · 先于模式选择）：

〇·1 素材来源（第 1 道锁）：
1. 原创       —— 从零构思
2. 改编       —— 已有小说 / 网文 / 大纲 / 剧本
3. 对标爆款   —— 指定一部剧，先采风出《对标情报卡》
4. 热点速成   —— 只给方向，先找选题方向

回复示例：3（对标爆款）
```

**〇·1 素材来源执行要点**：

- **未确认前，不进入第 0 步模式选择**——不登记来源、不生成 IP / 分集 / 正文；
- **③ 对标爆款 / ④ 热点速成**：**先挂载 `sd-recon-engine` 出《对标情报卡》并经用户确认**，再进第 0 步模式选择——**情报卡未确认 = 不进入创作**（对标不是照抄：情报卡的「⑩ 可迁移点 / ⑪ 不可迁移点」才是本环节的产出核心；只填热度不填迁移点 = 白采）；
- **④ 热点速成**：采风产出的是**"选题候选"**而非单剧卡；用户选定方向后按所选方向回到 ① 或 ③ 执行；
- **① 原创 / ② 改编**：**不挂载采风引擎**，直接进入第 0 步（**不额外增加步骤**）；
- **情报卡进入「① 来源登记」时**必须保留**来源与分级（T1 一手 / T1.5 准一手 / T2 二手）**；**禁止把 T2 讨论当设定依据、禁止把卡中「推断」写成「事实」**。

**素材来源写入项目状态**（`SCRIPT_PIPELINE_STATE.json` 与 `PROJECT_MANIFEST.md`），后续阶段不再更改。

### 第 -0.5 步：外来剧本检测与润色层（★ 2026-10-13 新增 · 只在「成型剧本」输入时触发）

**本步位于前置双锁之后、模式选择之前。判定口径（三条同时看）：**

```text
〇·1 = ② 改编 且 输入物是「已成型的剧本」（有场次划分 + 台词行）
        ↓
外部剧本体检（五条，命中 ≥1 即触发）
□ 台词行只有「角色：台词」、无（语气）位、镜行无神态？
□ 动作提示是结果性的、无过程相位？
□ 无状态栏（人物状态/情绪/伤势/道具位置）？
□ 关键台词无重音标注？
□ 相邻场次无因果连接？
        ↓
命中 → 挂载【外部剧本润色层】→ 产出润色稿 + 回签卡 → 用户确认 → 才进 P2/P3
全不命中（外部剧本已自带表演层）→ 免走，直接进 P2/P3（交接卡首行声明「免润色」）
```

- **规程唯一权威**：[external-script-polish.md](references/external-script-polish.md)；
- **润色边界（硬约束）**：**只补表演层（神态/动作相位/视线/语气位）+ 调度层（站位/进出场/过渡）**；⛔ **不得改台词、不得改事件、不得改人物**——那是越权重写；
- **发现硬伤**（人物降智 / 因果断裂 / 时间线矛盾）**只报告不修改**，出《润色发现清单》交用户裁定；
- **润色产出必须回签**——补出来的表演层是创作决定，用户逐条确认后才进 P3；
- **不适用**：〇·1 = ① 原创，或输入是小说/大纲/梗概（这两类走完整六阶段链，产出即自带表演层）。

### 第 0 步：模式选择

新项目尚未选择模式时，只显示：

```text
请选择制作模式：
A. 逐步确认（推荐）：每一步完成后由你确认，再继续下一步。
B. 完整执行：自动完成IP、全局开发、分集与剧本；每批剧本审核后仍暂停等待你选择。

回复示例：
- 回复：A
- 回复：B
```

### 六阶段链

```text
前置锁 〇·1 素材来源   → 总控 §〇·1（③④ 先经 sd-recon-engine 出《对标情报卡》并经用户确认）
→ 外来剧本检测（-0.5）   → 仅在「成型剧本」输入时触发 → references/external-script-polish.md（润色层 + 回签）
→ 模式选择                 → 本文件第 0 步
→ ①来源登记               → references/source-registration.md
→ ②IP 与角色开发         → references/story-bible-and-ip.md（IP 部分）
→ ③全剧开发圣经           → references/story-bible-and-ip.md（圣经部分）
→ ④分集规划【分集选择门】  → references/episode-planning.md
→ ⑤正式剧本【按批生产】    → references/six-stage-pipeline.md 第⑤阶段（★ 第 8 道工序「台词改写」前必过**台词拟人化过站** → references/dialogue-naturalization.md）
→ ⑥五席圆桌审核【用户决策门】→ references/roundtable-review.md
→ 用户决定：接受 → 下一批或完成剧本包；修改 → 一次精修/重写 → 回到⑥

※ 素材来源③④：《对标情报卡》进入 ①来源登记 时保留来源与分级（T1/T1.5/T2），
   T2 讨论不得当设定依据、卡中「推断」不得升格为「事实」。
```

每阶段：进入条件 → 生成全部文件 → 按阶段校验清单逐项自检 → 锁定或 `AWAITING_CONFIRMATION`。各阶段进入条件、产出物与门禁的完整定义见 [six-stage-pipeline.md](references/six-stage-pipeline.md)。

### 项目状态

每个项目创建：

- `projects/<project-id>/SCRIPT_PIPELINE_STATE.json`
- `projects/<project-id>/PROJECT_MANIFEST.md`
- `projects/<project-id>/00_source/SOURCE_MANIFEST.json`

阶段状态只允许：`NOT_STARTED / IN_PROGRESS / AWAITING_CONFIRMATION / AWAITING_USER_DECISION / LOCKED / STALE / BLOCKED`。锁定输入发生改变时，从变更阶段向下传播 `STALE`，不得静默沿用旧版本。

### 分集选择门

阶段④开始前，用户未明确集数方式时提供：`1. 智能推荐集数（推荐）` / `2. 用户自定义集数`（如「2，60集」）。用户只回复 2 没有数字时，提示「请告诉我想制作的总集数，例如：60集」，不得提前排集。内部只记录 `SMART_RECOMMENDED` 或 `USER_DEFINED`。详见 [episode-planning.md](references/episode-planning.md)。

### 圆桌审核与用户决策门

阶段⑥固定模拟两名主编和三类观众，必须标注 `AI_ROLE_SIMULATION`。五席先独立审读，再讨论并按固定权重计算 `S/A/B/NOT_READY`；等级只代表剧本层潜力，不预测真实播放量。任何等级统一写 `decision: AWAITING_USER_DECISION`，并显示：

```text
请选择：
1. 接受当前版本，进入下一批或完成剧本包。
2. 进行一次精修或重写，修改后提交下一轮审核。

回复示例：
- 回复：1
- 回复：2
```

`B/NOT_READY` 选择 1 时必须明确记录 `USER_ACCEPTED_QUALITY_RISK`，等级保持原值。没有用户选择时不得自动修改、写下一批或宣布项目通过。详见 [roundtable-review.md](references/roundtable-review.md)。

### 精修与复审

只有用户选择 `REFINE_OR_REWRITE` 记录后才能进入精修/重写。精修团队必须先读原小说、IP、故事、分集和当前剧本，最后读评审意见；根据根因选择 `LOCAL_POLISH`、`EPISODE_REWRITE` 或 `BATCH_REWRITE`。一次授权只生成一个正式新版本，目标 S、最低争取 A，但不保证等级、不追分魔改。修改后提交新一轮盲审；复审结束再次等待用户选择。详见 [six-stage-pipeline.md](references/six-stage-pipeline.md) 第⑦节。

### 长剧批次合同

正式剧本按连续集数分批，默认根据内容容量选择每批大小。每批必须：

- 读取本批全部来源原文、上一批末集完整剧本和连续性账本。
- 保存入口状态、变化、出口状态、钩子债务和下一批第一动作。
- 每集单独点开能看懂，同时上一集最后变化直接触发下一集第一动作。
- 首场前 10 秒包含来源支持的爆点、最小处境、行动问题和 `WHY_NOW`。
- 先形成局部兑现，再落具体且可支付的下一集钩子。

批次无法一次显示时继续写入项目文件，不压缩成梗概或碎片化节拍。

## 七、阶段校验方式

本技能不带独立机器校验脚本；各阶段的机器校验项（IP 十二项质量门、故事十五项质量门、分集质量门、剧本二十五项锁稿门、圆评六项硬门）一律转为**阶段校验清单**，由执行者逐项人工核对，全部 `PASS` 且 `failure_flags` 为空才能锁定。失败标记不得手工清空；先修改正文或账本，再重新逐项核对。缺少原小说、锁定上游、用户授权或连续性证据时输出 `BLOCKED_REPORT`。

## 八、最终交付

全部批次都经用户接受后，生成 `FINAL_SCRIPT_PACKAGE_MANIFEST.json`，列出：

- 来源范围与哈希。
- IP、故事、分集和最终剧本版本。
- 全部集数、批次与文件路径。
- 每批最终圆桌等级、用户决定和风险接受记录。
- 仍然开放的来源问题与后续制作禁改项（交 sd-asset-engine 的强制继承项）。

只声明 `SCRIPT_ADAPTATION_PACKAGE_COMPLETE`。不要声称已经生成资产、分镜或视频。

## 九、禁止越界

不把小说改成完全不同的故事；不因「爆款」目标牺牲来源因果和人物逻辑；不把每集切成互不相干的名场面；不使用假黑屏、半句话截断或重复上集代替钩子；不伪装真实观众调研；不让圆桌直接改正文；不让精修团队绕过原小说和锁定上游；不自动越过任何用户决策门；不越过本引擎边界去生产资产、分镜、投喂提示词或视频——那是 sd-asset-engine、分镜引擎和总控的职责。
